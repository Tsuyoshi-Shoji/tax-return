> 対象: 収支管理および確定申告アプリ。版: 0.1。作成日: 2026-10-08。
> 状態: 個人利用向け暫定設定。責任者・承認者・最終レビュー日: 本人 / 本人 / 2026-10-08。
> 実構成、対策の実装、試験結果は個人利用向けに整理済み。候補・計画を実施済みと扱わない。

## 個人利用の前提

単独利用を前提とし、指揮責任者・技術対応・証拠保全・個人情報・法務判断・利用者連絡・経営承認はすべて本人が兼務する。外部委託先、常設当番、複数承認者は置かない。連絡手段は本人の電話・SMS・別端末メールを基本にする。

代替連絡先は通常チャット・メールが使えない前提で、本人の別端末・電話・SMSを使う。クラウド、認証、AI等の窓口は通知期限だけ控え、外部委託先がないものは対象外とする。

## 重大度と内部目標案

| 重大度 | 判定例 | 受領確認の目標案 | 状況更新の目標案 |
| --- | --- | --- | --- |
| S1 緊急 | 秘密漏えい、認証侵害、広範改ざん、復旧不能 | 15分以内 | 30分ごと |
| S2 重大 | 限定漏えい疑い、悪用可能な秘密公開、主要停止 | 1時間以内 | 2時間ごと |
| S3 中 | 封じ込め済みの限定事象、影響が判明していない不審挙動 | 4営業時間以内 | 毎営業日 |
| S4 低 | 侵害兆候のない軽微な不備 | 1営業日以内 | 対応変更時 |

これは承認前の内部目標で、法定期限や24時間対応の実績を表さない。申告期限への影響、継続侵害、情報の機微性により格上げする。不明なら高い側で仮判定する。体制・当番・実行可能性を確認して承認する。

## 対応フロー

1. 検知・受付: INC-YYYY-NNNを採番し、検知時刻、報告者、対象、観測事実、影響の疑いを記録する。時刻はUTCとJSTを併記する。
2. 判定・招集: 本人が指揮責任者として、重大度、対象範囲、継続性、漏えい・改ざん・停止の有無を仮判定する。
3. 封じ込め: 関連エンドポイント、AIツール、共有、アカウント等を最小範囲で停止・制限する。侵害鍵・セッションを失効し、依存サービスへの影響を確認する。進行中の被害抑止を優先し、保全可能なログ等を並行取得する。
4. 証拠保全: 原本と作業コピーを分離し、取得者、時刻、取得方法、ハッシュ、アクセス履歴、受渡しを記録する。ログ、設定、監査履歴、必要なスナップショットを適法に保管する。秘密値を事故チケットへ貼らない。
5. 調査: 侵入口、侵害期間、利用者・資産・委託先・データ範囲、取得・改変・削除の可能性を確認する。確認済み事実と推測・不明を区別する。
6. 根絶: 原因修正、権限再設定、鍵再発行、悪性成果物除去を行い、関連箇所を確認する。証拠を消す再構築・一括削除は保全計画と指揮判断を経る。
7. 復旧: 信頼できる構成・バックアップを選び、認可、帳簿整合性、削除済みデータの扱い、監視、原因修正を検証する。本人承認後に段階復帰する。
8. 通知: 本人が適用法令・契約、報告先、期限、起算点、報告内容を確認し、必要な場合のみ文面と実施を管理する。調査完了前でも必要な初報は遅らせない。
9. 終結・改善: 影響と残余リスクを記録し、再発防止の担当・期限を設定する。risk-register.md、control-mapping.md、security-test-plan.mdを更新する。

## 事象別の初動

| 事象 | 封じ込め・調査・確認 |
| --- | --- |
| 他利用者データへのアクセス | 該当API・出力・検索を制限。認可条件とアクセス履歴を確認し、T-001,T-002,T-011で修正検証 |
| 認証秘密・API鍵漏えい | 失効・再発行・利用先更新。リポジトリ履歴・CI・呼出し履歴を調査し、T-009で再検査 |
| 帳簿改ざん | 更新処理を制限。履歴・元証憑を保全し、復元候補の借貸・残高・訂正履歴を確認 |
| AIへの誤送信 | 該当送信・検索・ツールを停止。送信項目・提供者保持条件を確認し、必要な削除依頼・通知を判断 |
| ランサムウェア | 侵害系統を隔離し、バックアップ権限を保護。検証済みの復元元と再侵害防止を確認 |
| 提供者停止・DoS | 制限・障害遮断・手動代替を実施。重複処理・データ損失・期限への影響を確認 |
| 端末紛失・退職者アクセス | アカウント・セッション・端末権限を失効。暗号化・持出し・遠隔消去可否を確認 |
